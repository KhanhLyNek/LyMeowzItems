# LyMeowz server migration (Paper 26.3)

## Runtime names and commands

- `AgarthaLib` (Bukkit identity) -> **LyMeowzLib**, main command `/lymeowzlib`; original `/agartha` alias retained
- `MyItems` (Bukkit identity) -> **LyMeowzItem**, main command `/lymeowzitem`
- Legacy `/myitems` and `/agarthalib` command roots are **not** registered; the `provides` aliases only resolve plugin dependencies and `PluginManager.getPlugin()`
- All *other* Bukkit commands and aliases (including `/myitem`, `/mi`, `/itematt`, `/lore` and `/enchant`) remain as before
- New canonical nodes `lymeowzitem.*` and `lymeowzlib.*` work. Both legacy `myitems.*` and `agarthalib.*` permission nodes remain valid during migration. Keep existing permissions as-is until you choose to migrate your permission groups.
- All existing `Path_*` keys from `Resources/data.yml` are now parsed by `com.lymeowz.item.config.DataDefinitions`; the original `DataConfig` Java API remains and forwards its setup to the new reader. Live Paper checks ensure command, dependency, item database, and language paths have not changed.
- The companion LyMeowzLib plugin manager provides `com.lymeowz.lib.manager.PluginServices` via `PluginAccess.of(LyMeowzLib)`, preserving command registry identity and providing read-only language snapshots plus the original placeholder values. The real Paper startup test validates this ABI between both production plugin JARs.
- Item generator YAML decoding now lives in `com.lymeowz.item.config.ItemGeneratorDefinitions` using the original type/tier managers and the original legacy `ItemGenerator` builder. `ItemGeneratorConfig` still owns setup, file migration, and old signatures. The canonical `ItemGeneratorDefinition`/`ItemGeneratorRegistry` interfaces expose read-only metadata snapshots from the same live builder/manager instances; IDs, type/tier weights, `Names`/`Name`, `Flags`/`ItemFlags`, and lore remain unchanged. An invalid or removed tier is now handled by a null check rather than an item-generation NPE. The live Paper probe exercises YAML aliases, original registry identity, immutable canonical views, and missing-tier handling.
- Item type/tier configuration YAML parsing now lives in `com.lymeowz.item.config.ItemTypeDefinitions` and `ItemTierDefinitions`. Original `ItemTypeConfig`/`ItemTierConfig` retain setup, old-file migration and Java APIs. The legacy `ItemType`/`ItemTier` builders now also implement read-only `ItemTypeDefinition`/`ItemTierDefinition`; the existing live manager objects implement `ItemTypeRegistry`/`ItemTierRegistry`, available through `GameServices.itemTypes()` and `.itemTiers()`. Original slot NBT, stats modifiers, enchantment grades, material/data and YAML IDs are not renamed or reserialized. Canonical ID/enchantment views are immutable snapshots. Live Paper tests validate default registries, YAML decoding and damage/health modifier values.
- Item database YAML reading now lives in `com.lymeowz.item.config.ItemDefinitions`, using the same Bukkit deserialization, existing `convertToGame` converter and colorization order as before. The original `ItemConfig` retains its database migration, write/erase operations, public method signatures and `@MyItems` lore format; neither item IDs nor metadata are reserialized by this reader. The Paper live probe verifies case-preserving keys, non-item filtering and clone semantics without changing server files.
- Element YAML parsing is now implemented in `com.lymeowz.item.config.ElementDefinitions`, preserving only the user-file lookup, historical key aliases, potion grade/chance/duration clamps, and legacy lore coloring. Existing `ElementConfig` delegates to this implementation while retaining its original setup/migration and Java signatures. Original `Element` builder now also implements the new read-only `ElementDefinition` view; new `GameServices.elements()` and `items()` project the original manager instances without re-serializing any item. The canonical item catalog uses the original cloning read path, and canonical ID/resistance views are unmodifiable snapshots.
- Existing `ElementRegistry` now exposes potion metadata safely through `ElementDefinition.potions()` and the canonical `ElementPotionDefinition` + immutable `ElementEffect` record. The original `Element` and `ElementPotion` builders are still the *same live instances* with their original mutable legacy getters and unchanged constructors; new API values are detached map snapshots. Element IDs, resistance, grade, chance and duration gameplay calculations are unchanged, and no potion is applied during tests. Paper CI verifies registry identity and live-versus-snapshot behavior.
- Skill configuration parsing now lives in `com.lymeowz.item.config.AbilityWeaponDefinitions`: packaged defaults load first, user YAML overrides second, and the original `AbilityWeaponConfig.setup()` still migrates the same old file path and retains its public getters. New `GameServices` and `GameAccess.of(LyMeowzItem)` expose the **same live** `GameManager` and weapon registry instances without a second manager or mutable canonical property ID collection. Existing builder classes and YAML skill IDs are unchanged. Paper integration checks include the original 25 skill properties and synthetic invalid-grade/mixed-case configuration values.
- New-plugin developers can use `WeaponAbilities.registry(LyMeowzItem)`, `WeaponAbilities.find(LyMeowzItem, id)` and `WeaponAbilities.all(LyMeowzItem)` with only LyMeowz public types. These facade methods return the original live weapon instances, while the canonical collection view is unmodifiable to prevent accidental registry corruption. The original manager collection signature remains unchanged for binary compatibility.
- The 25 existing weapon ability singletons now implement the canonical `com.lymeowz.item.ability.WeaponAbility` interface through the original `AbilityWeapon` base. Legacy attribute interfaces also extend canonical read-only base/cast/effect interfaces without altering method descriptors. `AbilityWeaponProperties` implements `WeaponProperties`; its original scaling math moved intact into `AbilityScaling`. `RegisterAbilityWeaponManager` implements `com.lymeowz.item.manager.WeaponRegistry`, and legacy case-insensitive ID lookups delegate to `WeaponLookup` without replacing the original registry or altering registered IDs.
- `/lymeowzitem model` now executes in `com.lymeowz.item.command.ModelCommand`. Old `Paper26ModelCommand.execute(CommandSender,String[])` remains as a compatibility API; permissions, ItemsAdder/Oraxen model selectors and original item gameplay metadata still use the same implementation.
- The MythicMobs 5 event/config adapter runs in `com.lymeowz.item.integration.MythicEventAccess`, with the legacy `Paper26MythicEventAccess` class and constructor kept as delegating ABI. Existing event, YAML, drop and equipment processing semantics stay unchanged.
- Lore number parsing now executes in `com.lymeowz.item.stats.LoreStatsNumbers`, including the existing six enum `Kind` values. The old `Paper26LoreStatsNumbers` and its old nested enum remain as binary-compatible API bridges; the live LoreStatsManager uses the new implementation. The JVM tests compare parsing of every kind across the old/new names.
- Existing combat, critical, accuracy, PvP/PvE and durability formulas now execute in `com.lymeowz.item.stats.CombatMath`; `com.lymeowz.item.modern.Paper26StatsMath` forwards its original 13 public methods unchanged. Pure Java tests compare old/new math, including 0%/100% chance and saturating durability.
- Command YAML decoding now lives in `com.lymeowz.item.command.CommandDefinitions` and `com.lymeowz.lib.command.CommandDefinitions`. The historic `CommandConfig` classes remain loadable and keep the original externally visible `CommandBuild` IDs and aliases. Help text is decoded through `com.lymeowz.lib.command.CommandText`, with the old `Paper26CommandText` facade retained.
- Both Paper plugin entrypoints now live at `com.lymeowz.lib.LyMeowzLib` and `com.lymeowz.item.LyMeowzItem`, delegating to the preserved historic base classes without reimplementing lifecycle or gameplay. More runtime code now lives in `com.lymeowz.lib.permission`, `com.lymeowz.lib.migration`, `com.lymeowz.item.permission`, and `com.lymeowz.item.stats`. Legacy Java APIs remain as delegating facades. Other `com.praya.*` and `api.praya.*` classes remain until their callers and serialization contracts can be migrated with tests. PAPI IDs, NBT keys, YAML command IDs, and item storage formats are intentionally unchanged.
- Gradle artifact IDs are **LyMeowzLib** / **LyMeowzItem** under the historic `com.praya` group; the GitHub repository URLs are not renamed in this update

## Upgrading a server

1. Back up the entire `plugins/` folder, worlds, player data and inventory/ender-chest data.
2. Remove the **old JARs** (AgarthaLib and MyItems); never install old and new JARs together.
3. Install both new LyMeowzLib and LyMeowzItem JARs together on Paper 26.3, then restart the server.
4. On startup both plugins copy *missing files only* from `plugins/AgarthaLib/` to `plugins/LyMeowzLib/` and from `plugins/MyItems/` to `plugins/LyMeowzItem/`. They preserve old folders, refuse to follow symlinks, and do not overwrite files already in the new folders.
5. Migrate any explicitly scripted `/myitems` root to `/lymeowzitem`. Other commands/aliases remain unchanged; existing `myitems.*` permission nodes remain valid.
6. Existing plugins with `depend: [AgarthaLib]` or `depend: [MyItems]` can resolve via the new Bukkit `provides` aliases. Plugins that explicitly compare `getName()` to the old name or hard-code the old command roots still require updating. Java API class names remain compatible.

Help and console guidance loaded from old or default language YAML automatically render the new command roots. The historical default `&aMyItems` chat prefix is displayed as LyMeowzItem; custom replacements are otherwise untouched. The shipped language/placeholder YAML stays frozen for legacy data compatibility.

The original `resources/Resources/dependency.yml` and `resources/Resources/command.yml` are frozen for item/command compatibility. The runtime dependency resolver transparently translates old `AgarthaLib` hard-dependency entries to `LyMeowzLib`.

CI validates both manifests, runtime registration of new commands, preservation of old aliases, and migration of disposable legacy data directories.
- Power Command YAML now reads through `com.lymeowz.item.config.PowerCommandDefinitions`, retaining legacy IDs, direct-string/list/nested `Command.OP` and `Command.Console` formats, execution order and Consume behavior. `GameServices.powerCommands()` exposes the **original** live `PowerCommandManager`; `PowerCommandDefinition` offers detached immutable command-line snapshots, while existing mutable legacy getters and command execution remain unchanged. Malformed scalar YAML sections are skipped without crashing.
- Socket/Gem metadata is now available as `GameServices.sockets()` via the original live `SocketManager`, `SocketGemsTree` and `SocketGems` instances. The new `SocketRegistry`/`SocketDefinition`/`SocketGemDefinition` interfaces return detached, unmodifiable ID/grade snapshots and cloned Bukkit `ItemStack` views. Legacy socket maps and RPG stat formulas, success rates, YAML layout, lore and raw NBT are unchanged.
- The original `SocketConfig` still owns YAML path migration, reset and public getters, but its unchanged grade/item/stat parsing is now in `com.lymeowz.item.config.SocketDefinitions`. The legacy gem builder remains authoritative; original success-rate caps, `Effect`/`Effects` aliases, type/grade text, item flags and lore are not reformatted. Non-section root/effect YAML nodes are ignored safely rather than throwing startup exceptions. A real Paper fixture checks the parser and original socket/gem registries.
- The original Item Set loader now delegates YAML parsing to `com.lymeowz.item.config.ItemSetDefinitions.read(FileConfiguration)`. All legacy IDs, component IDs, generated item attributes, stat bonus math, ability-trigger metadata and file traversal order remain unchanged. Non-section Bonus/Effect/Stats/Ability_Weapon/Component/Enchantment YAML nodes are skipped; a missing folder or directory entry no longer crashes startup.
- Item Set APIs are now available via `GameServices.itemSets()`: the original `ItemSetManager` provides `ItemSetRegistry`, and live legacy `ItemSet`, `ItemSetBonus`, `ItemSetComponent` objects implement read-only canonical interfaces with unmodifiable detached ID/threshold/description/slot lists. Item generation, set bonus application and ability triggers continue to use the exact original Java methods.
